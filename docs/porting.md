# 把测距链路搬到设备端

> 之前 App 只采集，距离要 `adb pull` 回 PC 用 `sim/slide_pipeline.py` 算。
> 那就不是一把尺子，是一个数据记录仪。本文记录这一环怎么补的、以及怎么证明它搬对了。
>
> **2026-10-11 晚更新**：出口判据推倒重来（v1 条件 ZUPT → v2 两段静止夹运动），
> 本文已按 v2 重写。为什么换、换成什么，见 [`boundary-design.md`](boundary-design.md) §8。

---

## 1. 为什么必须搬

用户按一下按住式按钮、松手、等手机停稳后**屏幕上直接出数字** —— 这才是产品。
链路里的每一步都已被真机验证过（见 [`boundary-design.md`](boundary-design.md)、
[`calibration.md`](calibration.md)），所以这一环的正确性判据只有一个：
**设备端算出来的数，必须和 Python 算出来的数一样**。

## 2. 搬了什么

`app/src/main/java/com/thripleq/slideruler/probe/SlideMeasure.kt`，纯逻辑、零 Android 依赖，
与 `sim/measure2.py` 一一对应（v2 参考实现）：

| 步骤 | Python `measure2.py` | Kotlin `SlideMeasure.kt` |
|---|---|---|
| 时间基准 | `median(acc_ts 间隔)/1e9` | `median(dts)/1e9` |
| 边界对齐 | `locate(acc_ts, recv_elapsed_ns)` | `locate(acc, ns, n)` |
| 静止检测 | `rolling_max_std` / `rolling_max_norm` / `static_flags` | `rollingMaxStd` / `rollingMax` / `percentile` |
| 运动分组 | `mot` + 按 `GAP_S` 分组 + 取与按钮窗重叠最大者 | 同（`groups` / `bestOv`） |
| 窗口 | 运动段 ± `MARGIN_S`，两端拉回静止样本 | 同 |
| 校准段 | 运动之前那段验证过的静止（≤ `CAL_MAX_S`） | 同（`calLo`/`calHi`） |
| 姿态 | `solve_attitude_v2`（Mahony，只在静止段开修正） | `solveAttitude` |
| 去重力 | `to_linear(g_mag)` | `lz[i] = f.z - gMag` |
| 出口 | `zupt_two_anchor`（双锚点无条件去趋势） | `zuptTwoAnchor` |
| 误差棒 | 平台扫描（`PLATEAU_GRID` 网格） | 同 |
| 模型分歧 | `bare` vs `dist` → `modelSensitive` | `integrateEnd` vs `zupt.distanceM` |

**刻意不做**的两项：

- **单姿态标度修正 `k̂ = ‖g‖/9.81`**：单姿态下 `k̂` 混着零偏在重力方向的投影 `b·ĝ`，
  分不开（`b_z` 只要 0.05 m/s² 就装成 +0.5% 的标度）。
- **二次残差模型**（允许残差加速度线性漂移）：仿真里 6 参数 / 6 约束，窗口一短矩阵病态，
  偏差从 ±0.4% 涨到 −1~−2.6%、平台宽度涨 3~4 倍。只留线性。

## 3. 怎么证明搬对了

`app/src/test/java/.../SlideMeasureTest.kt`，**9 条断言、7 份真实采集夹具**
（连 `meta.txt` 里的触摸时刻一起），期望值由 `sim/measure2.py` 在同一份 CSV 上产出。

```
cd android && ./gradlew testDebugUnitTest
```

容差 `1e-6 m`（0.0001 cm）—— 比界面显示的 0.01 cm 精度还紧 100 倍，
只留给浮点求和顺序的差异（Python 的 `fmean`/`pstdev` 用精确累加，Kotlin 用朴素求和）。

**断言的不只是距离，还有下标和分支选择** —— 那才是判据本身。两套实现都可能跑出接近
15 cm 的数字，但"窗口落在哪 / 锚点取哪段 / 要不要拒答"差一点点，换一条采集就会崩：

| 夹具 | 情形 | 断言重点 | 距离 |
|---|---|---|---|
| `20261011_100631` | 完全静止 | 判"没动"，距离 0 | 0 cm |
| `20261011_100444` | 正常滑动 | 距离 + 平台 + 运动段/窗口/锚点下标 + 裸积分差 3% | 15.4156 cm |
| `20261011_100459` | 长停顿 | 停顿被裁掉（按住 1.87 s 但窗口 2.84 s）+ 修正量 46% 不报警 | 15.7530 cm |
| `20261011_100409` | 松手时还在动 | **模型敏感**（修正量是答案的 2.6 倍） | 6.8475 cm |
| `20261011_100555` | 尾部静止只有 0.048 s | 仍给数，但必须报终点锚点退化 | 1.0096 cm |
| `20261011_100601` | 按下前一直在动 | **拒答**，理由必须指向"按下之前" | 拒答 |
| `20261011_090006` | 尾部没静止段 | **拒答**（v1 在这里给过 15.91） | 拒答 |

外加两条负例：`DOWN >= UP` 的退化窗口、样本数不足，都必须**被拒绝**而不是给一个看似合理的数字。

## 4. 接入界面时唯一要小心的地方

**采到手机真的停下为止，不是固定时长。** v2 要用"运动结束后那段静止"当终点锚点。
松手时手机往往还在动（抬手那 0.1~0.3 s 里手机靠惯性继续前移），那段静止得先采进缓冲区。

`MainActivity` 的收尾逻辑：UP 之后等**连续静止 400 ms** 才收工（`SLIDE_SETTLE_DWELL_MS`），
上限 3 s（`SLIDE_SETTLE_MAX_MS`）。上限必须 ≥ 引擎的 `TAIL_S = 2.5 s`，否则引擎看不到尾部。

这一条是 v1 的账：v1 固定收尾 1.5 s，2026-10-11 那批采集里有 **10 条**数据结束时手机还在动
（末尾连续静止 0.00 s），引擎只能拒答。逐条查过，不是算法的错。

**引导文案也必须跟着改。** v1 的文案写的是「按住后立刻推，别先晃」——
而 v2 需要运动前有一段验证过的静止当**左侧锚点兼校准段**（≥ 0.25 s）。
按原文案做，用户会把手机往桌上一放就按、就推，起点侧没有静止段 → 只能拒答
（实测 100601 / 100608 就是这样被拒的）。现在的文案是：

> ① 把手机放稳，静置 2 秒 → ② 按住按钮 → ③ 按住停稳约半秒再推 → ④ 1~2 秒内推完，中间不停
> → ⑤ 松手 → ⑥ 手别碰，等手机停稳出数。

## 5. 移植时查出来的五个 bug

前四个会让引擎给出**看起来体面但错误**的结果，第五个只是死字段。都不是风格问题：

1. **开闭区间约定不一致**：`measure2.py` 内部把连续段存成半开区间 `[a,b)`，
   而 `window`/`motion` 是闭区间。Kotlin 统一报闭区间，于是"锚点末端"天然差 1。
   是逐位对齐的单测把它逼出来的 —— 距离和平台全对，只有这一个下标差 1。
   现在 Python 额外导出 `anchorInclusive`，两边可逐字对照。
2. **`DOWN == UP` 没被拦**：此时所有运动组与按钮窗的重叠都是 0，
   "取重叠最大的一组"退化成"取时间最早的一组" —— 会去测**按住之前**那一小段。
   实测 `100444` 上它报 0.06 cm 而不是 15.4 cm：数字看着无害，但它答的是另一个问题。
3. **拒答理由写死**：`100601` / `100608` 被误诊成"松手后没停稳"，实际是"按下之前一直在动"。
   误导的提示会把用户引向错误的修正动作（他怎么保持不动都没用）。
4. **`endHitBound` 判据写漏**：只判了"运动延续到搜索区末尾"，漏了"窗口右端顶到数据末尾"。
   `100555` 的终点锚点因此退化成 **1 个样本**却没有任何警示。
5. **`anchorResidual` 是死字段**：算的是修正**后**的锚点速度均值，构造上恒等于 0。
   改成 `anchorDrift`（修正**前**的均值，即"要去掉多少速度"）才有诊断价值。

## 6. 怎么判断一次测量可不可信

设备端除了距离，还会把"引擎看到的证据"一并显示出来。四个独立的坏消息，优先级从高到低：

| 字段 | 含义 | 界面上的说法 |
|---|---|---|
| `failReason` | 拒答（没有两端静止段 / 慢动作 / 退化输入） | 直接显示原因 |
| `noMotion` | 窗口内确实没动 | "手机没动"，距离 0 |
| `modelSensitive` | 修正量 > 答案本身 → 由模型假设决定 | "不可当真…请重滑一次" |
| `tailStaticS` | 松手后留下的静止 < 0.15 s | "⚠ 终点锚点退化，这个数不可靠" |
| `confidence` | 平台宽度 / 距离（端点抖动） | "稳 / 还可以 / 不稳" |

**为什么 `modelSensitive` 排在 `confidence` 前面**：平台只反映**端点抖动**，
反映不了"残差到底是不是线性的"这个模型分歧。真机上有 4 条采集修正量是答案的
150%~4590%（其中 `100424` 的裸积分 14.64 cm 被修成 2.12 cm），
它们的平台却分别只有 0.05~1.29 cm 宽 —— **平台窄在这里毫无意义**。
