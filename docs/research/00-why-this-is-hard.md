# 00 · 这个项目到底难在哪儿

> 给老板的技术入门，不是 spec。目标：读完你能自己判断每个技术决策是不是在扯淡。
> （放最前面：先懂问题，再看 01~05 的资料。）

## 一句话核心矛盾

**你有一个会漂的传感器，和一个把误差平方放大的算法，中间靠三根救命稻草续命。**

拆开讲。

## 1. 加速度计不测加速度，测的是"比力"

最反直觉的一件事：手机**静止放在桌上**，加速度计读数不是 0，是 **+9.81 m/s²**（重力反作用力，Z 轴朝上时）。

它测的物理量叫**比力**（specific force）：`比力 = 运动加速度 - 重力`。

所以你想要的"滑动加速度"（峰值才 ~1 m/s² 量级）是埋在一个 10 倍大的重力基准里的。**去重力去不干净，就等价于凭空捏造加速度**——这是本项目的命门，比传感器质量问题严重得多。

## 2. 三重误差杀手（为什么"积个分"会炸）

双重积分：`位移 = ∫∫ 加速度 dt²`。高中物理没告诉你的是误差怎么传播：

### 杀手一：零偏（bias）——误差按平方爆炸

传感器有个恒定的错误读数。校准能消大头，消不干净。

数值钉子：残余零偏 **0.05 m/s²**，滑 3 秒：
- 速度误差 = 0.05 × 3 = 0.15 m/s（线性涨）
- 位置误差 = ½ × 0.05 × 3² = **0.225 m**（平方涨）

0.05 的常数 bug 在你的 Kotlin 代码里只是个常数，在积分器里 3 秒变 22 cm。**没有任何"写得好的代码"能救常数零偏，只能靠边界条件打掉它（见第 4 节）。**

### 杀手二：姿态泄漏——比重零偏毒 3 倍

去掉重力需要知道手机此刻的朝向（姿态）。姿态估计错 1°：

```
假加速度 = 9.81 × sin(1°) ≈ 0.17 m/s²
```

**1° 姿态误差 = 一个 0.17 的零偏**，比传感器自身的零偏大一个量级。这就是为什么项目里一半的复杂度花在"姿态解算"上——不是为了知道手机朝哪，是为了把重力剥干净。

### 杀手三：白噪声

每个样本带 ~0.02 m/s² 的随机抖动（100Hz 下，消费级 MEMS）。单样本看是噪声/信号 = 1/50，不影响。但积分不会把噪声完全平均掉——它是误差地板的组成之一（ZUPT 打掉前两项之后，它开始主导）。

## 3. 陀螺仪是干嘛的：两个残废传感器互相扶

去重力需要姿态 → 姿态从哪来？陀螺仪测角速度，积分得姿态。

但陀螺自己有零偏（消费级 0.5~1°/s 很常见）——积分 3 秒姿态就漂 1.5~3°，又会把重力漏进来。鸡生蛋。

**传感器融合的本质：加速度计在手机准静止时就是"重力方向计"，可以反过来校陀螺积分出来的姿态。**

- 陀螺：短期准、长期漂（高频可信）
- 加速度计：长期指着重力方向不动摇、动态时被运动加速度污染（低频可信）
- 融合 = 高通用陀螺 + 低通用加速度计，互补滤波/Madgwick/Mahony 都是干这件事的不同写法

（**Yaw 不需要**：我们只关心 pitch/roll 把重力剥干净，航向漂移对一维测距零影响。别为 yaw 付复杂度。）

## 4. 三根救命稻草

### ZUPT（零速修正）：把物理事实变成硬边界

起点静止、终点静止——这是**物理事实，不是估计**。速度 v(0) = v(T) = 0 已知。

数值钉子：零偏引起的速度误差是**线性**的 → 强制首尾归零 = 用两个已知点把线性误差摊平到整段消掉 → 平方爆炸被掐死在萌芽里。

类比：浮点循环累积误差，但你知道初始值和理论终值，每轮跑完强制对齐，误差不带到下一轮。

我们的工况比文献里的好得多：步态 ZUPT 只有触地 50 ms 窗口，我们是**首尾各静止 1~2 秒**——静止检测稳如泰山。这是全项目最大的先天优势。

### 一维约束：白送 2/3 的噪声抑制

真实运动基本沿一条直线。把三维线性加速度投影到主方向（PCA），两个正交轴的噪声整段扔掉。三轴独立白噪声 → 只留一轴，误差直接砍约 √3。还顺带防"手滑歪了"：主方向估计对了，歪一点照样投影正确。

### 短时窗：1~3 秒

所有误差项都随时间涨（t²、t^1.5）。测 0.2~2 m 就是 1~3 秒的事——时间短是恩赐，也划定了产品边界（别想着拿它量 5 m，误差随时间爆炸不是线性恶化）。

## 5. 算一笔总账（为什么 spec 写 5%~15%）

0.8 m / 1.5 s、正弦速度剖面、加速度峰值 ~1.1 m/s²：

| 误差源 | 修正前 | 修正后 |
|--------|--------|--------|
| 零偏 0.05 m/s² | 22 cm | ≈ 0（ZUPT 摊平线性项） |
| 姿态 1° 泄漏 | 17 cm 量级 | 姿态滤波压到 0.3~0.5° → 数 cm |
| 白噪声积分 | ~cm 级 | 同左（ZUPT 后成主导项之一） |
| **合计** | **不可用** | **5~15 cm ≈ 6%~19%** |

对标：Wojtek 同管线先例（便宜 IMU、举重场景、机械臂测试）实测 ~12%。我们的条件比他好（手机 IMU 优于 $2 模组、滑动比举重干净、静止窗口长）——**瞄准带内偏优是合理的，超出这个带就是违反物理**。

## 6. 真机阶段才会暴露的坑（提前挂墙上）

1. **摄像头凸起会垫高手机**——"贴桌沿滑"的物理前提被镜头模组破坏，手机先天歪着滑，姿态压力变大。可能要"贴哪条棱"的产品设计
2. 中途犹豫停顿 0.5 s → 静止检测把测量切成两段，结果是半截。交互上要处理
3. 软桌面/桌布 → 信号糊；按下手指的压力变化会混入加速度
4. Android 传感器采样不均匀（jitter）——dt 必须用 `event.timestamp` 实测值，不能用假设的 10 ms
5. 刚从口袋掏出来温度冲击 → 零偏挪动 → 校准（那 2 秒静止）不是仪式，是每次测量的必需品
6. 厂商差异：请求 100 Hz 实际可能给 98~103 Hz，不同机器要体检

## 名词小词典

| 术语 | 人话 |
|------|------|
| 比力 (specific force) | 加速度计实际测的东西 = 运动加速度 - 重力 |
| 零偏 (bias) | 传感器的恒定错误读数 |
| 零偏不稳定性 (bias instability) | 零偏自己还会慢慢挪（温度等原因） |
| VRW / ARW | 速度/角度随机游走：白噪声强度的标准表达方式 |
| ZUPT | 零速修正：用"此处速度必为 0"的物理事实重置累积误差 |
| 互补滤波 | 陀螺（高频）+ 加速度计（低频）的频域拼合 |
| Madgwick / Mahony | 两种更花哨的互补滤波写法（梯度下降 / PI 控制器） |
| PCA | 主成分分析，找数据最"spread out"的方向，这里用来找滑动方向 |
