# 边界定位：把"算法检测"换成"按住式手动边界"

> 2026-10-11 · 由 `sim/exp_button.py` 的八组实验支撑。
> 结论先行：**这个方案比做亚采样变化点检测更好，而且更简单。** 但不是因为它"精确"，
> 而是因为它把"精确定位"这个需求整个取消掉了。

---

## 0. 一句话结论

积分窗口的边界**只要落在静止段内部**，误差就与"落得多深"无关 ——
所以按钮不需要精确，只需要**不越界**。用户天生的反应时间（看到按钮响应才推、
推到位才松手）方向恰好是安全的。实测：误差 **0.10%~0.14%**，与窗口余量无关。

---

## 1. 为什么边界是唯一剩下的瓶颈

`sim/README.md` 的记录：把边界定位这个变量摘掉，整条管线（姿态 → 去重力 →
一维投影 → ZUPT → 二次积分）在标称参数下的误差是 **0.07%**。而把边界加回来，
误差跳到**百分级**，且对起点尤其敏感（起点晚 10 ms ≈ −1.65%）。

体检 A（`docs/health-a.md`）又确认了这台 K40 的其它账都已结清：

| 项 | 结果 |
|---|---|
| acc 白噪声 | 0.0071 m/s²（比文档假设好 2.8×） |
| gyro 零偏 | 0.0007 °/s（≈0） |
| 时间戳 | 抖动 20 ns，无批次化 |
| acc 零偏/标度 | 9.4 mg / ≤+0.25%，且被校准段吸收 |
| **采样间隔** | **9.513 ms ← 一个采样点的边界误差 ≈ 1.6%** |

也就是说：**只要边界"snap 到某个采样点"，就先天带 ≈1.6% 的误差**。
这是目前唯一还站着的大项。

---

## 2. 物理洞察：为什么按钮不需要精确

设积分窗口 `[lo, hi]`，真值运动段 `[n₀, n₁]`。把窗口两端向外扩到静止段里：

```
   静止段         运动段           静止段
 |-----------|[===============]|-----------|
          lo↑                 ↑hi
```

静止段里线性加速度 ≈ 0（去重力之后），所以：

- **起点提前**：多积的那段 v≈0，不产生位移
- **终点延后**：同理

于是边界误差 ≈ 0，**无论提前/延后多少**。反过来才是灾难：

- **起点滞后**（切进运动段）：等于把速度从 0 抬起的那段真实位移整段丢掉 → 陡峭
- **终点提前**：对称，丢掉收尾位移

**这个不对称性是整个方案的支点**：安全侧是一个"平台"，危险侧才是斜坡。
按钮时刻的抖动只要小于安全余量，就被平台吸收。

## 3. 仿真验证

参数：K40 实测（`acc_noise=0.0071`, `gyro_bias=0.0007°/s`, `dt=9.513ms`），
运动剖面用摆线（加速度首尾连续，见 §4），0.8 m / 1.5 s，默认多颗种子取中位。

|---|---|---|
| 提前 999 ms | 80.10 cm | +0.13% |
| 提前 200 ms | 80.11 cm | +0.14% |
| **正好** | 80.11 cm | **+0.14%** |
| 滞后 48 ms | 79.33 cm | −0.83% |
| 滞后 105 ms | 76.41 cm | −4.48% |
| 滞后 200 ms | 67.43 cm | **−15.72%** |
| 滞后 504 ms | 23.67 cm | −70.41% |

### 3.2 终点锚点（起点固定在真值起点）

| 终点相对真值 | 距离 | 误差 |
|---|---|---|
| 提前 200 ms | 67.79 cm | −15.26% |
| 提前 48 ms | 79.43 cm | −0.71% |

两表镜像对称：**提前起点 / 延后终点 = 安全平台；反之 = 斜坡。**

### 3.3 按钮时间戳抖动：要多少安全余量

假设按下比真值起点早 margin、松手比真值终点晚 margin，两者各叠加 N(0, σ)：

| 安全余量 | σ=0 | σ=10 ms | σ=20 ms | σ=30 ms | σ=50 ms |
|---|---|---|---|---|---|
| 0 ms | 0.13% | 0.08% | 0.05% | −0.01% | −0.14% |
| 20 ms | 0.11% | 0.11% | 0.08% | 0.06% | 0.04% |
| **50 ms** | **0.12%** | **0.12%** | **0.12%** | **0.10%** | 0.06% |
| 100 ms | 0.10% | 0.11% | 0.11% | 0.11% | 0.11% |
| 200 ms | 0.10% | 0.10% | 0.11% | 0.12% | 0.12% |

**只要余量 ≳ 3σ 就完全免疫。** 人的反应时间天然提供 100 ms 级余量，
所以 σ 到 50 ms 都不构成威胁 —— 这意味着**按钮时间戳的精度根本不关键**。

### 3.4 副作用：两端带静止段会不会污染 PCA / ZUPT

| 余量 | 积分窗=PCA窗 | PCA 改用真值运动段 |
|---|---|---|
| 0 ms | 0.14% | 0.14% |
| 200 ms | 0.11% | 0.11% |
| 800 ms | 0.10% | 0.10% |

两列完全相同 → **静止段对 PCA 主轴无害**（运动段能量远大于静止段噪声，
λ₁/λ₂ 从 192 降到 93 但主轴方向不变）。

### 3.5 对决：按钮 vs 滑窗检测器（同一批合成数据）

| 设备 | 滑窗检测（现方案） | 按钮（余量 200 ms） |
|---|---|---|
| K40 实测 | −0.29% / −0.21% | **0.12% / 0.21%** |
| 教科书参数 | −0.49% / −0.18% | **−0.03% / 0.29%** |

（中位 / 最大）按钮**胜出**，而且它的误差是"平"的 —— 不依赖任何阈值标定。

### 3.6 真机验证（静止对照组）

第一次真机跑通（采集 `20261011_083634`）：用 `adb shell input swipe` 在同一点按住 3 秒、
松手，模拟"按住式边界"，但**手机全程没有移动**（真值距离 = 0）。
跑 `sim/slide_pipeline.py`：

| 检查项 | 结果 |
|---|---|
| 时间对齐 | DOWN 14.36 s → 样本 #1510；UP 17.37 s → 样本 #1826；按住跨度 3005 ms |
| 事件→送达延迟 | 2 ms / 1 ms（adb 注入绕过了触摸屏硬件，真手指会更长，见 §6） |
| DOWN 落在采样点之间 | 距上一采样 6.46 ms（一个采样间隔 9.51 ms） |
| 校准（DOWN 前 2 s） | \|g\|=9.9175、k̂=1.01096、σ_a=0.0083、b_g=0.00002 rad/s（与体检 A 一致） |
| 审计 DOWN | max‖a_lin‖ = 0.1291 < 阈值 0.2628 → **✓ 静止** |
| 审计 UP | max‖a_lin‖ = 0.1316 < 阈值 0.2628 → **✓ 静止** |
| **距离（按钮窗）** | **0.05 cm** ← 手机没动，应 ≈0 ✓ |

结论：**"边界落在静止段内 → 误差与深度无关"这条从仿真预测的规律，在真机上复现了。**
审计逻辑也按设计工作（两个边界都被判为静止）。

### 3.7 真机验证（第一次真实滑动）——数字对上了，但不可信 ⚠️

第二次真机是**真实手指**滑动（采集 `20261011_084700`，K40，按住 5347 ms，
用户报的真值 **34 cm**）。`sim/slide_pipeline.py` 给出：

| 检查项 | 结果 |
|---|---|
| 时间对齐 | DOWN 7.22 s → 样本 #759；UP 12.57 s → 样本 #1321 |
| 输入延迟 | 5 ms / 3 ms |
| 审计 DOWN | max‖a_lin‖ = 0.2963 > 阈值 0.2860 → **✗ 可疑** |
| 审计 UP | max‖a_lin‖ = 0.9629 → **✗ 可疑** |
| **距离（按钮窗）** | **34.95 cm（+2.80%）** |
| 外扩 200 ms | 38.99 cm，**与上者差 40.44 mm** ← 余量无关性**不成立** ✗ |
| λ₁/λ₂ | **2.5**（正常一维滑动应 ≫10；静止对照组是 9~500） |

距离数字很接近真值，**但不能采信**。决定性证据是**窗口端点扫描**——同一个采集，
只把积分窗口端点挪一挪，答案就会在 **0.0 ~ 44.5 cm** 之间乱跑，**没有任何平台**：

| 起点 \ 终点 | 1010 | 1100 | 1200 | 1260 | 1300 | 1321 | 1370 | 1391 |
|---|---|---|---|---|---|---|---|---|
| 700 | 0.8 | 17.5 | 21.5 | 8.9 | 37.9 | 37.7 | 44.5 | 11.4 |
| 759（=DOWN） | 0.3 | 15.3 | 18.4 | 9.0 | 35.3 | **35.0** | 40.9 | 10.0 |
| 900 | 0.0 | 8.8 | 9.1 | 11.2 | 31.2 | 30.7 | 34.7 | 9.1 |
| 1010 | — | 3.3 | 0.2 | 14.8 | 29.8 | 29.3 | 32.0 | 9.3 |
| 1080 | — | — | 4.7 | 15.6 | 26.8 | 26.1 | 27.6 | 8.0 |
| 1150 | — | — | 0.7 | 2.7 | 6.6 | 4.2 | 0.4 | 5.3 |

**没有平台** = 积分端点没有落在静止段里 = §2 那条物理洞察的前提被违反。
数字对得上（+2.8%）是巧合。

看点：起点取 1150（10.94 s）时，无论终点取哪，结果都是 0~6 cm ——
说明真正的位移发生在 1150 之前；而 `759→1010` 只有 0.3 cm、`759→1100` 却有 15.3 cm。
这种"不可加性"是 ZUPT 线性去趋势的斜率随端点变化造成的，也是端点不在静止段的旁证。

**信号本身说了什么**（逐样本）：

| 时段 | \|a_lin\| | 陀螺范数 | 判读 |
|---|---|---|---|
| 5.7 ~ 7.1 s（DOWN 前） | ~0.11 | ~0.001 | 静止 |
| 7.23 s（DOWN） | 0.296 | 0.018 | 手指压屏的小脉冲 |
| 7.3 ~ 10.2 s | ~0.11 | ~0.002 | 仍像静止（无陀螺） |
| **10.3 ~ 12.5 s** | 0.3 ~ 0.9 | **0.08 ~ 0.26** | **有转动 —— 这是"被搬动"而不是"沿桌沿滑"** |
| 12.57 s（UP）之后 | 0.3 → **1.36** | 0.05 ~ 0.47 | 松手后手机仍在被移动/抬起 |

两个硬事实：**① 手机在"滑动"期间有明显的姿态转动**（陀螺 0.26 rad/s ≈ 15°/s，
而纯沿桌滑行几乎不应有转动）；**② 速度在整个窗口里从未回到 0**（原始积分终点
v = −0.35 m/s 且还在增大）—— 即**松手时手机还在动**，用户没有做到"推到位停稳再松手"。

**排除法：不是"滑得太慢"惹的祸。** 用 K40 参数在仿真里把工况换成慢速滑动
（窗口两端各留 0.3 s 安全余量）：

| 位移 / 时长 | 平均速度 | a_peak | \|误差\|中位 | 最大 |
|---|---|---|---|---|
| 80 cm / 1.5 s | 53.3 cm/s | 1.755 | 0.10% | 0.32% |
| 34 cm / 1.2 s | 28.3 cm/s | 1.165 | 0.09% | 0.32% |
| **34 cm / 2.3 s（≈本次）** | 14.8 cm/s | 0.317 | **0.33%** | 1.48% |
| 34 cm / 4.0 s | 8.5 cm/s | 0.105 | 96.7% ← 已低于分辨力 | 99.9% |

慢到 34 cm / 2.3 s 时按钮方案仍只有 **0.33%** 中位误差。所以这次的失败
**不是算法退化，是操作没有把边界落在静止段里**。

另一次采集 `20261011_084515`（按住 1908 ms）更差：按钮窗 18.15 cm、λ₁/λ₂ = 7.5、
外扩差 88.4 mm、检测器窗给 163 cm —— **整条废弃**。

### 3.8 真机验证（15 cm，带稳定度指示灯）——查出两个真 bug ✅

加上实时稳定度指示灯重新装了 App 后，用户又滑了一次：采集 `20261011_090006`
（K40，DOWN 10.37 s / UP 14.77 s，**按住 4395 ms**，真值 **15 cm**）。

旧管线给 **12.24 cm（−18.4%）**。逐层拆开，发现两个和"慢速滑动"耦合的独立缺陷：

**缺陷 ①：去重力写死 9.81，而不是本机实测的重力模长。**

K40 静止段实测 ‖g‖ = **9.9129**（标度 k̂=1.0105）。`remove_gravity` 按 `a_lin = q·f − 9.81`
计算，于是静止段凭空留下 **0.101 m/s²** 的残余——正好是 ‖g‖−9.81。实测静止段
|a_lin| 均值 0.1044，是加速度噪声地板（0.0082）的 **12.7 倍**。

这在慢速滑动里是致命的：15 cm / 4.4 s 的真实运动加速度只有 **0.049 m/s² 峰值**，
比残余还小 → **PCA 会把主轴选到"重力方向"上去**。仿真里这直接导致输出 ≈0：

| 15 cm / 4.4 s（K40 参数，20 个种子） | 误差中位 | 最大 |
|---|---|---|
| `g_mag = 9.81`（旧） | **−98.5%** | 100.0% |
| `g_mag = ‖g_meas‖`（修） | **+0.19%** | 1.9% |

修后静止段残差 |b| = **0.0028 m/s²**（`max‖a_lin‖` 从 0.104 → 0.0528）。

⚠️ 注意这**不等于**打开 `use_scale_corr`。那条路是拿单姿态 ‖g‖ 去反推标度因子 k，
会被 b·ĝ 污染（见 `Params.use_scale_corr` 的警告）。这里只是把**同一个**静止段测到
的重力模长直接用作去重力的基准——它的唯一含义是"让静止段的 a_lin 归零"，而静止段
归零本来就是 ZUPT 的前提，不需要任何标定假设。

**缺陷 ②：无条件 ZUPT 在长窗口下把真实位移一起扣掉了。**

原 ZUPT 无条件把积分终点的原始速度 `v_end` 强制归零，等价于扣掉 `|v_end|·T/2`
的位移。本次 `v_end = +0.0138 m/s`（1.4 cm/s），T = 4.40 s：

```
无条件 ZUPT :  12.24 cm   ← 扣掉 3.03 cm
裸积分      :  15.27 cm   ← 真值 15 cm，+1.8%
```

`|v_end|·T/2 = 0.0138 × 4.40 / 2 = 3.04 cm`，与差值一模一样。**这个杠杆随 T 线性增长**，
而 v_end 本身又随 T 增长 → 长窗口下无条件是灾难。窗口内原始位移曲线也证明裸积分是对的：
p(t) 单调爬到 15.02 cm（t=14.58 s）、15.27 cm（UP），正是一条 15 cm 慢滑的样子。

**修法：条件 ZUPT。** 只有当 |v_end| 大到"用已知残余零偏解释不了"时才去趋势：

```
thr = |b|·T + 3·σ_a·√(T·dt)          # |b| = 校准段 a_lin 均值模长
|v_end| ≤ thr  →  手机已停稳，零偏攒不出这么大的 v_end  →  裸积分
|v_end| >  thr  →  手机确实还在动                        →  去趋势
```

四个真机采集全部验证通过（`sim/slide_pipeline.py`）：

| 采集 | 真值 | 时长 | v_end | 阈值 | 判定 | 结果 | 误差 |
|---|---|---|---|---|---|---|---|
| `20261011_083634` | 0 | 3.01 s | +0.0002 | 0.0043 | 裸积分 | **0.02 cm** | ✓ |
| `20261011_084700` | 34 | 5.35 s | −0.3250 | 0.2296 | 去趋势 | **34.91 cm** | +2.7% |
| `20261011_084515` | — | 1.91 s | +0.0764 | 0.0201 | 去趋势 | 18.12 cm | — |
| **`20261011_090006`** | **15** | 4.40 s | +0.0138 | 0.0173 | **裸积分** | **15.27 cm** | **+1.8%** |

阈值系数 k 的鲁棒性：把 `k=2…8` 全扫一遍，**四个真机采集的判定与结果一字不变**
（要触发去趋势的 `084700` v_end=−0.325 远超阈值，该走裸积分的 `090006` v_end=0.0138
远低于阈值），所以这不是一个需要精调的旋钮，默认 k=3。

**残余误差的来源：窗口太长。** 即使修好这两条，误差仍随 T² 涨：

| 15 cm 滑动时长 | 误差中位 | 最大 |
|---|---|---|
| 0.8 s | 0.17% | 0.53% |
| 1.5 s | 0.45% | 0.98% |
| 2.3 s | 0.81% | 2.66% |
| 4.4 s | 2.79% | 7.49% |

所以操作提示要加一句：**按住之后尽快滑完、停稳就松手**——4 s 滑 15 cm 是本次
余下误差的主因。另有两次采集是无效的：`20261011_085650`（DOWN/UP 同一事件时刻，
按住 0 ms，全程静止，76 s）为误触，已丢弃。

### 3.9 真机验证（第二次 15 cm，按住 1.81 s）——又查出两个更深的缺陷 ✅

采集 `20261011_091811`：K40，DOWN 3.98 s / UP 5.78 s，**按住 1807 ms**（用户按新引导
把时长压进了 1~2 s），输入延迟 3 ms，真值 **15 cm**。

**旧管线给 13.17 cm（−12.2%）**。逐层拆开，是两个比 §3.8 更靠底层的问题。

#### 缺陷 ③：一维投影（PCA 主轴）自带 cos θ 的损失

旧出口是"取加速度方差最大的方向当主轴，把 a_lin 投上去再积两次"。但我们要的是
**净位移**的方向，而 PCA 给的是**加速度方差最大**的方向 —— 两者只在轨迹是完美
直线、且侧向噪声各向同性时才重合。真机上一次都不重合：

| 采集 | PCA 主轴与净位移方向夹角 θ | 投影自带损失 cos θ |
|---|---|---|
| `091811`（本次，1.81 s） | **22.6°** | **0.923（−7.7%）** |
| `090006`（上次，4.40 s） | 16.3° | 0.960（−4.0%） |
| `084700`（34 cm） | 47.9° | 0.670（−33%） |
| `083634`（静止对照） | 87.7° | 0.041（主轴 = 纯噪声） |

`091811` 的净位移是 `[−1.53, −15.40, +0.79] cm`，模长 **15.50 cm**；投到 PCA 主轴上
只剩 14.28 cm。**那 8% 是被投影丢掉的，不是信号里没有。**

**改法：直接取三维净位移矢量的模** `|∫∫ a_lin dt²|`。它在定义上就等于"起点到终点"
的直线距离，不需要估计任何主轴，损失项恒为 0。代价只有一个：若轨迹中途折返，
`|净位移| < 实际路程` —— 所以窗口终点必须落在折返之前（见缺陷 ④）。

#### 缺陷 ④：松手时手机还在动，按钮窗把位移截掉了

松手那一刻（#608）：

* 前向速度 **+0.0201 m/s**，而阈值（零偏 + 噪声能解释的上限）只有 0.0156 m/s；
* 松手后手机又往前走了 **228 ms**，位移在 #632 见到顶 **15.62 cm**；
* 随后被手拉回来，一路退到 10.60 cm。

也就是说按钮窗 `[DOWN, UP]` 把"往前最后那一段"整个截掉了 —— 直接量松手点 = 13.72 cm，
补上那段 = **15.63 cm**。

**改法：判据复用。** 条件 ZUPT 本来就要问"终点速度是否大到已经停稳解释不了"，
那就用同一个 `thr` 再决定一件事：

```
|v_end| ≤ thr  →  手机已停稳  →  终点 = 松手点，且不去趋势
|v_end| > thr  →  手机还在动  →  终点顺延到停稳区里前向位移最大处
```

顺延的实现（`pipeline.stop_endpoint`）不能用"速度过零"找停稳点：从松手点起积分，
速度天生从 0 开始，判据是瞎的。一律从按下点积分拿绝对速度，然后
（1）找第一个 `|v_fwd| ≤ thr` 且持续 50 ms 的样本 → 停稳区起点；
（2）往后扩到 `|v_fwd|` 重新超阈 → 停稳区终点；
（3）在 `[松手点, 停稳区终点]` 内取**前向位移最大**的那一帧。手机停住后可能原地不动
（位移平台），也可能被手拉回去（折返）—— 两种情况"位移见顶"都指向同一个正确终点。

顺延后阈值系数从 3 提到 **5**：`091811` 在 k=3 时的判定余量只有 3%（0.0124 vs 0.0121），
等于一个随机开关；k=5 后余量 19%。漏触发只是留着零偏那点小误差，误触发会凭空
砍掉一段真位移 —— 所以判据要"宁可不动手"。

#### 结果

三维净位移 + 统一松手判据 + 顺延，重跑全部真机采集：

| 采集 | 真值 | 旧出口（1D + k=3） | 新出口 | 新出口误差 |
|---|---|---|---|---|
| `083634` 静止对照 | 0 | 0.02 cm | **0.59 cm** | +5.9 mm |
| `090006` 15 cm / 4.40 s | 15 | 12.24→15.27 cm | **15.91 cm** | +6.1% |
| `091811` 15 cm / 1.81 s | 15 | **13.17 cm** | **15.63 cm** | **+4.2%** |
| `084700` 34 cm | 34 | 34.91 cm | 36.74 cm | +8.0% |

#### 仿真验证早松手（`exp_release.py`）

真机上"松手早一点"的后果没法反复重现，所以做成仿真：造一条完整 15 cm 滑动，把按钮窗
人为截在运动进度的 `frac` 处。

| 截在运动 | 直接量 误差中位/最大 | 顺延后 误差中位/最大 | 顺延触发率 |
|---|---|---|---|
| 50% | 83.62% / 84.07% | **0.93% / 2.40%** | 100% |
| 70% | 71.73% / 72.22% | **1.01% / 3.37%** | 100% |
| 90% | 11.00% / 11.76% | **1.01% / 4.52%** | 100% |
| 100%（不该顺延） | 0.78% / 2.53% | 0.78% / 2.53% | **0%**（不误触发） |

**这一条把"早松手"从"整条作废"降成"正常误差"，而且误差与松手时机无关。**
注意直接量那一栏：截断位置从 90% 走到 50%，误差从 11% 涨到 84% —— 用户完全感觉不到
自己松早了，但数字会崩。这就是为什么它必须在算法里兜住，而不是靠嘱咐。

#### 打假：加速度计增益修正是个陷阱（这次真被证明了）

K40 静止实测 `‖f‖ = 9.913`，比标称 `9.80665` 高 **1.1%**。看起来"增益偏高 1.1%，
应该除回去"，而且推理也对：去重力用的是实测 `‖g‖`，所以 `a_lin = k·a_true`，
净位移整体偏 `k` 倍。

但 `k̂ = ‖f‖/g` **同时含零偏投影**：`‖f‖ ≈ k·g + b·ĝ`。仿真里把 `acc_scale` 设成 1.0
（无增益误差），测出来的 `k̂` 中位仍是 **1.0096** —— 因为 K40 的 z 轴零偏 9.4 mg
（=9.4e-4 g）投影进了 `‖f‖`。反过来也一样：真机上 `0.092/9.81 = 0.94%` 的"增益"
可能全是零偏。**单姿态估不出干净的 k**，所以这一项不开。（要分离 k 与 b 需要
≥4 个不共面姿态做球面拟合，见 `docs/calibration.md`。）

仿真里的定量对照（15 cm / 1.81 s，20 种子）：

| 真实 acc_scale | 增益修正 | 误差中位 | 误差最大 |
|---|---|---|---|
| 1.0000 | 关 | **−0.23%** | +2.39% |
| 1.0000 | 开 | −1.18% | +1.43% |
| 1.0113 | 关 | +0.90% | +3.53% |
| 1.0113 | 开 | −1.17% | +1.42% |

开了修正在**没有增益误差时**也会把结果拉低 1.2% —— 因为它修掉的是零偏。所以关。

#### 残余：真机一致偏高 +4~6%，仿真对不上

仿真（含 K40 的零偏/噪声/增益）说这套出口的偏差是 `−0.2% ~ +0.9%`，最大 +3.5%。
但真机上 15 cm 两次都偏高 4.2% / 6.1%，34 cm 偏高 8.0% —— **同向、量级一致**。
仿真里没有的东西：滑动中的真实旋转（`091811` 松手瞬间陀螺 0.31 rad/s）、真实轨迹的
弯曲、以及"用户报的 15 cm 本身就有 ±0.5 cm 的肉眼误差（±3.3%）"。
在拿到更硬的真值（比如用尺子固定起止刻线）之前，不再往下猜。

第一版实验用的是正弦速度剖面（`sine`），结果窗口一加余量误差就从 0.65% 跳到 **2.2%**，
看起来像是"余量有害"。**这是我自己仿真真值的瑕疵**：

正弦速度剖面对应的加速度是 `a(t) = a_peak·cos(πt/T)`，**在起点处 a(0) = +a_peak ≠ 0**
—— 加速度从静止段的 0 **跳变**到最大。梯形积分在跳变处会多算半步 `a_peak·dt/2`，
这个假速度持续整个运动段，产生 ≈1.3%/端 的系统偏差。

但真实的手推**不可能**在起点瞬间产生最大加速度。摆线剖面（位移 ∝ `1−cos`）
的加速度首尾都为 0，才是物理真实的形态。对照：

| 余量 | sine（不物理） | cycloid（真实） |
|---|---|---|
| 0 ms | 0.653% | 0.139% |
| 100 ms | **2.239%** | 0.131% |
| 800 ms | **2.208%** | 0.100% |

**教训（第二次了，见 `sim/README.md` §5）**：仿真真值的运动学连续性必须和真实运动一致，
否则会在算法上伪造出根本不存在的失效模式。

## 5. 设计决策与防错

### 5.1 选按钮，不做亚采样检测器

仿真已经回答了"要不要做亚采样变化点检测器"：**不需要**。按钮方案的误差（0.12%）
已经低于滑窗检测器（−0.29%），而且它不依赖阈值标定、不依赖噪声地板估计。
一个纯粹为"定位边界"服务的亚采样算法，在目标函数上已经输给了一个 UI 控件。

### 5.2 但危险侧仍然存在，所以要"用算法审计按钮"

按钮的安全区是个平台，可一旦用户操作错误（按下后立刻推、或推着没停就松手），
误差会从 0.1% 直接跳到 −15% 甚至 −70%。这个失效模式不能靠 UI 提示兜住。

**关键设计**：让算法从"定位者"降级为"审计者"。

| | 定位（原方案） | 审计（新方案） |
|---|---|---|
| 任务 | 在数据里找出运动的精确起止时刻 | 判断"DOWN 时刻附近手机是否静止" |
| 难度 | 需要亚采样插值，受信噪比限制 | 只需阈值判断，**容忍一个采样点的误差** |
| 谁提供边界 | 算法 | 按钮 |

审计规则（用已有的自适应噪声地板做阈值）：

```
DOWN 巡检：检查 [DOWN−0.3s, DOWN+0.3s] 窗内 ‖a_lin‖ 是否都在静止阈值内
UP   巡检：同理
若任一巡检失败 → 本次测量标注"边界可疑"，提示重测
```

这样把"必须做对"从"算法必须精确检测"转移到了"用户必须按对"，
而后者有一道可自动执行的验收关卡。

### 5.3 界面引导（已实现）

App 里按住式按钮的引导文案（2026-10-11 §3.9 后更新）：

> ① 先静置 2 秒（学本机噪声底）→ ② 按住 → ③ 稍停 → ④ 推 → ⑤ 停稳，等指示灯变绿 →
> ⑥ 绿灯后再等半秒，然后松手，别再碰手机。
> **松手那一刻必须还是绿的。灯是红的就松手 = 本次作废** —— 手机会继续往前滑，
> 那段位移算不回来。
> 按住到松手尽量控制在 1~2 秒内 —— 拖得越久误差越大。

四个动作里，"稍停"和"停稳"是给安全余量用的，"按住/松手"才是边界事件。

§5.3 原本写的是"松手后别再碰手机"就够。§3.9 之后这句话不够了：`091811` 那次用户
**松手那一刻灯是红的**（前向速度 +2.0 cm/s > 阈值 1.56 cm/s），松手后又往前滑了
228 ms。所以文案必须说清"红灯松手 = 作废"，并把"绿灯后再等半秒"写成硬动作 ——
§3.9 的顺延虽然能把这一段救回来，但那是**事后补救**，正面做法仍然是不让它发生。

**实时稳定度指示（2026-10-11 加，§3.7 的直接产物）**

§3.7 那次真实滑动失败的根因是「松手时手机还在动」——而这恰恰是**用户当场看得见**的。
所以把它做成界面上的一个绿/红指示灯：

```
取最近 40 个样本（≈0.38 s）：
  accStd = 三轴标准差的较大者        （指南 §7 判据三，不需要姿态解算）
  gyrMax = 陀螺范数峰值              （指南 §7 判据二）
  thr    = max(4 × 本机地板, 绝对下限)
  负荷   = max(accStd/thr_acc, gyrMax/thr_gyr)     负荷 < 1 → 绿灯
```

本机地板在录制的**前 2.5 s** 学（取运行最小值），之后**冻结**——不冻结的话最小值会一直下探、
阈值越来越紧，静止时也会抖成"在动"。绝对下限取 `accStd=0.10`、`gyrMax=0.03`
（K40 实测 σ_a≈0.019、σ_g≈0.006 的约 5 倍），防止某台机在进入界面时手就在抖、
把地板学成运动量而永远显示绿灯。

刻意**不用「‖f‖ 偏离 9.81」**那条判据做指示器——它在横向几乎瞎（见 `sim/README.md` 勘误 ①）。

真机静止实测：`aσ 0.007~0.013、ω 0.002、负荷 0.07~0.13×` —— 离 1 有 8~14 倍余量，
不会误报。**这一项把 §3.7 的失效模式从"事后发现"变成"当场可见"。**

**补一条引导：尽快滑完（§3.8 的直接产物）**

§3.8 查明余下误差随按住时长 T² 增长（0.8 s 时 0.2%，4.4 s 时 2.8%，最大 7.5%）。
所以引导文案里"稍停 → 推 → 停稳"要强调**别拖时间**：稍停和停稳只是留安全余量，
不是让你慢慢挪。15 cm 这种短距，按住到松手控制在 **≈1.5 s 以内**最稳。

**再补一条：松手判据（§3.9 的直接产物）**

§3.9 证明"松手太早"在算法里兜得住（顺延到停稳点，见 `exp_release.py`），但那是
补救。正面做法是让用户松手时灯必须是绿的 —— 因为红灯松手时手机上还有 2 cm/s 的
前向速度，位移曲线会在松手后继续爬 0.3~2 cm，最终数字落在哪取决于用户松手多早，
是用户完全感知不到的随机性。

## 6. 仿真覆盖不到、只能靠真机回答的

| 风险 | 为什么仿真答不了 |
|---|---|
| **触摸事件的真实精度** | `MotionEvent.uptimeMillis` 只有 ms 精度；从手指接触玻璃到系统报点还有几 ms 延迟，且这个延迟有抖动。仿真里我把它建模成 σ=50ms 都测不出危害，但那只是模型 |
| **输入延迟** | `recvUptimeMs − eventMs` 要真机量。已写进 `meta.txt`，这次采集会带回来 |
| **手指按压的干扰** | 手指压在屏幕上会产生局部应力，可能进加速度计。仿真无法建模 |
| **用户能不能"按住同时推"** | 交互可行性问题。手机要能被一只手按住屏幕的同时推动 |
| **时钟基准一致性** | `MotionEvent` 用 uptimeMillis、`SensorEvent` 用 elapsedRealtimeNanos。屏幕常亮时二者只差深度睡眠时间（应为 0），但要实测确认 |
| **滑动中手机在转** | 仿真里姿态是固定的。真机 `091811` 松手瞬间陀螺 **0.31 rad/s**、窗口内 90 分位 0.156 rad/s。旋转会把侧向伪加速度带进 `a_lin`，还会污染重力方向（§3.9 的残余 +4~6% 有一半嫌疑是它） |
| **真实轨迹未必是直线** | 三维净位移只对直线轨迹等于路程。用户沿竖直面推、面未必精确竖直（用户自己也提醒过），轨迹可能弯。仿真里轨迹恒为直线 |
| **用户"真值"本身的精度** | 目前 15 cm / 34 cm 都是用户目测报的，±0.5 cm（±3.3%）量级，与残余误差同阶。要分离算法误差和真值误差，需要固定的起止刻线 |

因此 App 的 `meta.txt` 里同时留档 `event / recv_uptime / recv_elapsed` 三个量 ——
前两个算输入延迟，第三个用于和 `acc.csv` 对齐。
